# Observability on Grafana Cloud (Part B)

OpenTelemetry in the app, the engine, the weekly jobs and the eval scripts sends traces, metrics and logs straight to your **Grafana Cloud**
stack's OTLP gateway (no collector, no Docker). Run records live in Supabase (`observability.*`) and are read by Grafana through a read-only
role. Six dashboards and ten alert rules are generated from code and uploaded with `python -m observability.cloud`.
Step-by-step: [`GO-LIVE.md`](GO-LIVE.md). Spec and decisions: [`docs/production-llm-cloud-observability-plan.md`](../docs/production-llm-cloud-observability-plan.md).

> **Status: written and tested against fakes, never run against a real stack.** The OTLP export (including the Basic-auth header) is
> verified against a fake collector, and the sync tool against a fake Grafana API. Nothing has been seen working in a live Grafana Cloud
> stack: dashboard rendering, OTel→Prometheus metric names, Loki's `detected_level` label and alert delivery are the likeliest first-run fixes.
> Alert delivery goes to a **placeholder webhook** until you choose a channel (decision D3). No production host (D2).

## What you do (account steps are yours; keep every secret in `.env` files, never in chat)
1. **Create / open a Grafana Cloud stack** (free tier is fine to start). Note its URL, e.g. `https://<stack>.grafana.net`.
2. **OTLP credentials** — stack → *OpenTelemetry → Configure*: copy the OTLP endpoint, the instance ID, and create a token with
   `metrics:write`, `logs:write`, `traces:write`.
3. **A service account** — *Administration → Users and access → Service accounts*: create one (Admin is simplest), add a token.
4. **Supabase** (for the Run explorer / Product usage panels): review and apply `db/migrations/0010_observability.sql`
   (`python -m db.migrate`), then `alter role grafana_ro login password '…';` and note the *pooler* host. Restrict by IP if you can.
5. `cp observability/.env.example observability/.env`, fill it in. Then:

```bash
python -m observability.cloud check              # tests the OTLP credentials (traces/metrics/logs) and the service-account token
python -m observability.cloud headers            # prints OTEL_EXPORTER_OTLP_HEADERS=…  → copy that line (and the endpoint) into
                                                  #   the root .env and frontend/apps/web/.env.local
python -m observability.cloud sync               # DRY RUN: shows what would be created
python -m observability.cloud sync --apply       # folder, Supabase datasource, 6 dashboards, 10 alert rules, placeholder contact point
```
`sync` is idempotent (re-running updates in place) and never changes your notification policy unless you add `--policies`
(that replaces the stack's whole routing tree). `--no-postgres` leaves the Supabase datasource out.

## Pointing the app at it
```bash
OTEL_EXPORTER_OTLP_ENDPOINT=https://otlp-gateway-prod-<region>.grafana.net/otlp
OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20<from `python -m observability.cloud headers`>
TELEMETRY_DB_URL=postgresql://…        # run records → Supabase observability.* (falls back to SUPABASE_DB_URL)
TELEMETRY_HASH_SALT=<long random>      # user ids are HMAC-hashed with this
```
Set these where the processes actually run: the Next server (`frontend/apps/web/.env.local`), the engine (inherits the app's env), and the
shell that runs `scripts/weekly_selection_run.sh` / the eval scripts. With none of them set everything behaves exactly as before.
The free tier's retention is fixed by Grafana (about 14 days for metrics / logs / traces), not the 30 / 14 days in the draft plan.

## Live verification checklist (not yet done)
1. Run the app; compile → screen → confirm one prompt.
2. *Explore → Tempo*: `{ name = "prompt.run" }` — one trace with `prompt.compile`, `prompt.screen`, `prompt.confirm`, `interpreter.parse`, engine spans (`screen.filter`, `data.fetch`).
3. *Explore → Prometheus*: `llm_requests_total`, `prompt_run_duration_seconds_bucket`, `tool_calls_total` exist (confirms the OTel→Prometheus naming the dashboards assume).
4. *Explore → Loki*: `{service_name="prompt-screener-web"} | event="end"` shows one line per task / agent / tool with `trace_id` (structured metadata); check `detected_level` exists for the Errors panel.
5. **Run explorer**: pick the prompt id; tasks / agent calls / tool calls appear and link to the trace. If the tables error, check the Supabase datasource (*Connections → Data sources → Supabase (runs) → Test*).
6. `python -m scripts.emit_job_metrics`, then `last_over_time(screener_job_last_success_timestamp[30d])` in Explore.
7. Fire a test alert (lower a threshold in the UI) and confirm the placeholder webhook receives it.

## Layout
| Path | What |
|---|---|
| `build.py` | **source of truth** for the 6 dashboards and the 10 alert rules: edit, `python -m observability.build`, commit |
| `grafana/dashboards/*.json` | generated by `build.py` (what `sync` uploads, after mapping datasource uids) |
| `cloud.py` | `headers` and `sync` commands: Grafana HTTP API client, dry-run by default |
| `metrics-catalog.json` | every metric the dashboards / alerts use and the code token that emits it (tests keep them honest) |
| `redaction-fixtures.json` | shared by the TS and Python redaction tests |
| `.env.example` | everything the tooling reads |

## Notes that differ from the draft plan
- No Alloy / Docker / Pushgateway. Redaction is done in-process only (the Alloy second layer is gone).
- Batch gauges (`screener_*`, `golden_suite_accuracy`) go over OTLP; a pushed series goes stale minutes after its process exits, so every
  dashboard / alert reads them with `last_over_time(…[30d])`, and "Weekly run missed" alerts on *no data* too.
- `screener_*` gauges use the label **`screener_job`**, not `job` (reserved).
- `prompt_run_duration_seconds` is the *processing time of each request* (labels `stage`, `outcome`), not wall-clock since the draft was created. The "interpreter too slow" alert uses `stage="compile"`.
- Engine-side spans are `screen.filter` and `data.fetch`; the TS client's calls to the engine are `engine.*`, so the two never double count.
- Product-usage panels read run records only; watchlist sizes and per-condition usage live in the app's own SQLite store.
- Alerts are Grafana-managed rules created through the provisioning API.
